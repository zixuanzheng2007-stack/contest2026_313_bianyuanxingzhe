## 一、这是什么产品（给外人一句话）

**边缘行者**是戴在腰后的接近提醒：后面有电动车、电自靠近时，腰带自己响、自己亮，提醒你让路。

- **给谁用：** 走路、过马路的人（先做台架演示，不做成品腰带量产）。  
- **解决什么：** 后面来的车很静，人回头看不过来。  
- **我们做成什么样就算成功：** 台架上有车靠近 → 板子自己判断 → 发出人能听见/看见的提醒；同时能用简单对话问「现在后面有没有车」。  
- **我们不是什么：** 不是汽车雷达、不是导航、不是只靠聊天回答「有没有车」。测远近由雷达和板子自己算，聊天只负责说明和帮忙执行提醒。

一句话定位：**腰后雷达看靠近，板子自己决定响不响；智能助手负责主动提醒，不代替测距。**

---

## 二、总目标（初赛必须同时做到两件事）

1. **感知这条线：** 雷达看到靠近 → 板子判断「该不该提醒」→ 蜂鸣 / 屏幕 / 灯 至少有一种人能感觉到。  
2. **比赛要求的智能助手：** 能在板子上跑起来；有 **1 条技能说明**（例如「接近提醒」）；靠近时**不用人先问**就会去执行提醒；串口里能问一句「现在有没有来车」。

缺第 2 条，这个赛道交不了。

本期**明确不做：** 导航、骨传导耳机、两颗雷达同时主用、复杂云端协作。2417 只当 2451 的备用雷达。

建议门限（可改）：**正在靠近，并且大约 15 米以内 → 提醒。**

## 三、系统怎么拆（主程序 + 独立组件）

整体是 **一个主程序**，烧进同一块开发板。里面几块可以分开写、分开测，最后装在一起。

```text
                    ┌─ 主程序（板上只跑这一份）─┐
雷达 ──► 读数组件 ──► 判断组件 ──► 提醒出口 ──► 蜂鸣/屏幕/灯
                         │
                         └──► 智能助手（技能 + 主动执行提醒）
                                    ▲
                              人可以问一句近况
```

| 组件 | 负责人 | 它独立负责什么 | 不负责什么 |
|------|--------|----------------|------------|
| **真机环境** | 郑子轩 | 接线、供电、烧录、拍演示 | 不独自改判断公式（三人说好再改） |
| **主程序骨架** | 郑子轩 | 板上主流程串起来、能编能烧、和硬件对得上 | 不包办全部算法细节 |
| **读数** | 王筠昊 | 把雷达数字读进来，整理成「距离、快慢、是否靠近」 | 不决定响不响 |
| **判断 + 应用逻辑** | 王筠昊 | 按门限给出「提醒 / 不提醒」；写好应用侧流程 | 不直接管喇叭怎么响 |
| **提醒出口** | 郑子轩为主，王筠昊配合接口 | 接收「响哪一档、为什么」，驱动蜂鸣/屏/灯 | 不重新算距离 |
| **智能助手** | 韦政宇 | 靠近时主动调用提醒出口；回答「有没有来车」 | 不用它来测距、不当唯一判官 |

这样拆的好处：硬件和主程序在郑子轩处收口；王筠昊专攻数据和业务逻辑；韦政宇专攻智能体，可用假信号先练。

## 四、联调时大家认准的接口（先冻结，改名要三人同意）

组件之间只认这几样，不要每人自己发明一套：

| 名字（对内） | 人话 | 谁提供 | 谁使用 |
|--------------|------|--------|--------|
| 距离、速度、是否靠近 | 现在后面多远、多快、在不在靠近 | 王筠昊（读数） | 判断、助手、演示 |
| 判断结果 | 该不该提醒、什么原因 | 王筠昊（判断） | 提醒出口、助手 |
| 提醒出口 | 「第几档 + 原因」一句话调用 | 郑子轩实现，王筠昊定调用方式 | 判断或助手来调用 |

约定：

- 韦政宇侧助手**只调用提醒出口**，不自己写喇叭细节。  
- 技能建议就叫「接近提醒」：写清何时提醒、怎么调用出口、用户能问什么。  
- 郑子轩测板时，对方要写清：测哪个版本、期望看到什么（灯亮 / 响一声 / 打印一行字）。

## 五、具体任务（按人，能勾选）

### 郑子轩 · 硬件 + 主程序

- 接好雷达电源和数据线（先断电再改线；电源正负不要接反）。  
- 负责主程序骨架：能稳定编译、烧进板子、板子能进操作界面。  
- 主雷达优先用原来的 2451；坏了再用 2417 备用，并拍照、记清接法。  
- 实现或落实「提醒出口」到蜂鸣 / 屏幕 / 灯（与王筠昊约定好调用方式）。  
- 按队友给的版本上板联调，回传：好不好用、照片/短视频、屏幕上看到什么。  
- 截止前交出 **1 段台架短视频**（有靠近 → 有提醒）。

### 王筠昊 · 数据处理 + 应用编写

- 雷达数据读入与整理：距离、速度、是否靠近。  
- 判断逻辑：靠近且约 15 米内 → 要提醒。  
- 应用侧流程编写：从「有数据」到「给出判断 / 调用提醒」写清楚。  
- 与郑子轩对接提醒出口的调用方式；与韦政宇对接「判断结果 / 假信号」格式。  
- 写出别人能照做的复现步骤（3～8 步）。

### 韦政宇 · 智能体

- 智能体能在板子上跑起来，基础对话能通。  
- 写好 1 条「接近提醒」技能说明。  
- 用「假靠近」先跑通：一到门限就主动执行提醒，不必人先说话。  
- 真雷达通了之后，换成王筠昊给出的真实判断结果再演示一遍。  
- 给作品说明准备一小段「智能体做了什么」的人话。

### 三人共同

- 只改本队仓库，用分支合并，不把板子寄来寄去。  
- 每周至少 2 次真机联调窗口（板在郑子轩处）。  
- 提交前：作品说明、演示不超过 5 分钟、过程记录按赛方要求放进仓库。

## 六、阶段验收（有日期、有「怎样算过」）

今天起大约 5 周到 9 月 20 日。日期可按实际加减两天，但**每一阶段必须有能给别人看的结果**。

### 第 0 段 · 环境能干活（建议 8/16–8/19）

**目标：** 电脑能编出板子程序；郑子轩能烧进去。

**怎样算过：**

- [ ] 虚拟机里工程能编过（含比赛要求的助手示例）。  
- [ ] 郑子轩能烧录，板子能进操作界面。  
- [ ] 三人知道：板在郑子轩那里，改线先断电。

**交什么：** 一句「编过 / 烧过」+ 板子界面截图或照片。  
**主责：** 郑子轩收口；王筠昊、韦政宇各自虚拟机也能编过一遍。

### 第 1 段 · 板上有数（建议 8/20–8/25）

**目标：** 雷达数字进板子，判断有结果。

**怎样算过：**

- [ ] 板上能看到距离（或备用雷达也能看到原始数字）。  
- [ ] 判断结果能打印或显示：「提醒 / 不提醒」。  
- [ ] 接线有一张对照照片。

**交什么：** 一段日志或屏幕照片，能看出距离和判断。  
**不过就停在这，不进入「好看的提醒」。**  
**主责：** 王筠昊（数据与判断）+ 郑子轩（接线与主程序联调）。

### 第 2 段 · 靠近能感觉到（建议 8/26–8/30）

**目标：** 人靠近或拿物体模拟靠近，板子有声或有光。

**怎样算过：**

- [ ] 走一次「靠近」动作，蜂鸣或屏幕有变化。  
- [ ] 提醒走统一出口，不是三处各写各的。  
- [ ] 有 20 秒以上录像。

**交什么：** 短视频 + 复现步骤。  
**主责：** 郑子轩（提醒出口与录像）+ 王筠昊（应用触发逻辑）。

### 第 3 段 · 智能体会主动提醒（建议 8/31–9/10）

**目标：** 智能体在板上；靠近时自己执行提醒；人可以问一句近况。

**怎样算过：**

- [ ] 智能体能对话（问「现在有没有来车」有回答）。  
- [ ] 到门限时，**人不用先问**，提醒也会发生。  
- [ ] 有 1 条写好的技能说明。  
- [ ] 可用假信号先验收，再换真雷达复验一次。

**交什么：** 演示录像（对话 + 主动提醒）+ 技能说明文本。  
**主责：** 韦政宇；郑子轩协助上板；王筠昊提供真实/假判断数据。

### 第 4 段 · 能提交（建议 9/11–9/20）

**目标：** 评委 5 分钟能看懂。

**怎样算过：**

- [ ] 作品说明：是什么、给谁、现场怎么演示。  
- [ ] 台架完整走一遍：靠近 → 提醒 → 能问答。  
- [ ] 仓库合并到可提交状态；赛方要求的记录放好。  
- [ ] 写明本期没做的（导航等），避免评委以为漏做。

**交什么：** 说明文档 + 终版短视频 + 仓库。  
**主责：** 三人共同；郑子轩出终版录像；王筠昊、韦政宇各补一段说明。
