# ESP32 USB依赖与网络稳定性排查

## 真实对照与结论边界

在同一块 SF32、同一版板上固件 `ew-20261025-esp-probe1` 下：

- 初始连续3次 AT 查询均收到完整 OK，每次6字节，UART overrun/frame/noise为0，未发送软件复位。USB状态当时未单独询问确认，记录为“尚待隔离”；此前明确接着ESP USB的成功证据另见 `uart_diag_20261025_1/esp_probe_after_usb_boot.json`。
- 用户确认仅拔掉 ESP32 USB，保留 SF32 USB及杜邦线后，6次握手均0字节；原有 AT+RST 回退也未恢复。UART错误计数0不能证明ESP正常供电。证据：`network_stability_20261025/usb_removed_observation.json`，原始捕获 `wifi_scan_capture_20261025_171820.txt`。
- 用户随后提供SF32排针图并明确纠正：**SF32 J0117物理1号脚3V3 → ESP32板上3V3**，不是VIN。此前“3.3v vin”和简短确认被助手误解为接VIN，因此供电入口错误/额外稳压器压降假设撤回，不应要求用户按此改线。现有用户接法与3.3V直接供电相符；供电能力、压降、接触/共地、EN/启动状态与UART接收问题仍需分项验证，不能由USB插入后恢复就认定任一项为根因。
- 热点扫描不可见此前已由用户确认是频段问题并恢复，与此次基础AT完全无回应独立。

乐鑫 DevKitC 官方将 USB、5V/GND 与3V3/GND列为不同供电方式，且要求只使用一种供电方式。用户板为CH340K的WROOM-32开发板，不能仅凭芯片型号就断言其VIN电路完全等同官方DevKitC。参考：[官方供电说明](https://docs.espressif.com/projects/esp-idf/en/v5.0.4/esp32/hw-reference/esp32/get-started-devkitc.html)。核实具体板卡后再选择额定输入；不要把5V接到3V3或GPIO。

## 已完成的稳定性修改（尚未上板）

所有固件改动集中在 `ew_wifi_at.c`；保留原来的单一AT锁、逐字节发送、UART映射、波特率、Wi-Fi凭证和离线预警。

1. 将等待AT锁由无限等待改为最多500ms轮询预算，避免长扫描/HTTPS占用时后续请求一直排队。此值是代码等待预算，系统调度可能增加实际墙钟耗时。
2. 锁忙不再发布“物理链路已断”；保留上次网络状态并发布AT_BUSY错误。扫描返回既有BUSY错误码，区别于模组故障。
3. 检查 ATE0 与 CWMODE=1 的完整OK和错误返回；配置失败不再宣称唤醒成功。
4. 删除任意 `OK` 后缀判成功的分支，拒绝 `NOTOK` / `BROK` 假阳性，只接受完整OK行。
5. 固定115200失败提示不再错误声称“所有波特率都试过”。

没有新增自动重启循环，没有改ESP32 NVS或固件，不以软件重试代替供电修正。预警页仍存在仅更新启动网络文案的旧限制，网络/串口结果与屏幕文字需要分开判断；本批次未混入UI改动。

## 下一步验收

维持现有SF32物理1号3V3→ESP32 3V3接线，不改接VIN。保持SF32固件不变，ESP USB保持拔除，先测ESP板3V3对其GND及EN对其GND电压，并与SF32源端3V3比较；静态正常不能排除无线发送时瞬态跌落。核对供电/共地接触、EN启动状态和板载USB串口复位电路，结合UART接收排查。获得稳定无USB工作后至少3次AT和一次扫描成功，再验证3次冷启动、热点连接/重连及雷达并行。条件稳定后才备份现有应用区、安装本候选并进行同样验收，区分硬件条件与软件加固效果。没有外部可控供电或仪器时不能冒称完成电气根因验证。
